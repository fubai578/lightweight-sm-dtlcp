# 09 · STM32F103C8T6 上板操作指南（地阔星 F103C8T6 + ST-Link V2 + CP2102）

> 适用硬件：**立创·地阔星 STM32F103C8T6**（Cortex-M3 @8/72MHz，64KB Flash / 20KB RAM，**无硬件 RNG**）  
> 配套：**ST-Link V2**（烧录）、**CP2102 USB-TTL**（串口看结果）、**W5500**（真机协议，见 §7）
>
> 与 `docs/08`（F407 流程）的差别集中在三处，已全部在本工程处理妥当：  
> ① **无 RNG** → 熵源换成 ADC 噪声 + 白化（§5）；  
> ② **无 FPU / 架构是 M3** → 编译选项与链接脚本都不同（§3）；  
> ③ **只有 64KB/20KB** → 32KB 适配证明与 RAM 预算要重新做（§4）。
>
> 本目录 `embedded/cortex-m3/` 是**新增的独立工程**，与 `embedded/cortex-m4/` 并存、互不影响。

## 0. 前置条件与时间预算

| 项  | 要求                                    | 状态             |
| -- | ------------------------------------- | -------------- |
| 硬件 | F103C8T6 + ST-Link V2 + CP2102（杜邦线若干） | ✅ 已购           |

#    预期：KAT/自检 FAIL 数 = 0、10 行 RESULT、summary.fail=0

## 2. 接线

> **⚠ 2026-10-14 实测：本机 ST-Link V2 驱动未装，走不了 SWD。**
> 系统里设备枚举为 `USB\VID_0483&PID_3748` 但 **Status=Error、Class/Service/DriverVersion 全空**
>（"硬件在、没绑驱动"），`openocd` 报 `Error: open failed`，
> `pyocd list` 报 `No available debug probes`。
> 装 WinUSB 驱动需管理员权限 + ST 官网下载（本次被站点安全策略拦截，HTTP 567）。
>
> **两条路，按下表选一条：**

| 方案 | 前置 | 命令 | 备注 |
|---|---|---|---|
| **A（推荐先用）** UART ISP | CP2102 插上 + BOOT0 拨到 1 | `python uart_isp.py --bin smc_m3_opt.bin` | **零驱动**，芯片自带 bootloader；烧完拨回 BOOT0=0 |
| B SWD | 给 ST-Link 装 WinUSB 驱动（管理员） | `pyocd flash --connect-under-reset smc_m3_opt.elf` | 能调试、能读回，优先争取装上 |

### 2.0 方案 A：UART ISP（不需要 ST-Link，CP2102 即可）

本仓库已自带烧录器 **`embedded/cortex-m3/uart_isp.py`**（实现 STM32 USART bootloader 协议）。

```bash
# 1) CP2102 插上 → 设备管理器应出现 "CP2102 USB to UART Bridge (COMx)"
# 2) BOOT0 跳线拨到 1（接 3V3），按一下复位
# 3) 烧录（脚本会提示确认）
cd embedded/cortex-m3
python uart_isp.py --bin smc_m3_opt.bin          # 不带 --port 会自动扫描串口
python uart_isp.py --port COM3 --bin smc_m3_opt.bin
# 4) ★ 烧完把 BOOT0 拨回 0（接 GND），按复位，否则下次上电不进自己程序
```

**代价（必须知道）**：ISP **不能读回、不能调试**（SWD 的单步/断点/变量查看都没有），
但烧录本身可靠、串口日志照样能看。传输 33 KB 约 10–20 s。

**排错**：脚本报"芯片无应答"时按顺序查——① BOOT0 是否拨到 1 ② 烧录前是否按了复位
③ TX/RX 是否**交叉**（CP2102 TX→PA10、RX→PA9，直连不交换是不行的）④ 板子 3V3 有没有电。

### 2.1 ST-Link V2（烧录，4 线）

| ST-Link | F103C8T6              |
| ------- | --------------------- |
| SWDIO   | SWDIO（PA13）           |
| SWCLK   | SWCLK（PA14）           |
| GND     | GND                   |
| 3.3V    | 3V3（**板子已有独立供电时不要接**） |

> ⚠ 本工程**不配置 PLL**，跑复位默认的 **HSI 8MHz**，所以板子不接晶振也能工作——  
> 这是首次上板最省事的做法。想跑 72MHz 见 §6.2。

### 2.2 CP2102（看串口输出，3 线）

| CP2102 | F103C8T6           |
| ------ | ------------------ |
| TX     | **PA10**（MCU 的 RX） |
| RX     | **PA9**（MCU 的 TX）  |
| GND    | GND                |

**不要接 5V/VCC。** 串口参数：**115200 8N1**，无流控。  
CP2102 是 **3.3V 逻辑**，可直接连 F103（PA9/PA10 非 5V 容忍也安全）。

> ⚠⚠ **串口没输出？先查 TX/RX 有没有接反（本项目 2026-10-14 实际踩到）**
>
> **CP2102 的 TX → PA10，CP2102 的 RX → PA9**。MCU 的 TX 出去必须进适配器的 RX，
> 所以两根线是**交叉**的，直连不行。这是「烧录成功但串口一片安静」的**头号原因**，
> 比驱动问题常见得多（本项目驱动装好后仍无输出，就是这一步）。
>
> **快速判定流程**：
> ① 先证明固件确实在芯片里（与接线无关）：
> ```bash
> pyocd flash -M under-reset -f 100k -t stm32f103rc -e chip smc_m3_opt.elf
> # 报 skipped 34816 bytes (17 pages) → Flash 内容与固件完全一致，固件侧没问题
> ```
> ② 若 30 秒无输出，把 TX/RX **对调**再试（最可能的修复）；
> ③ 仍无输出 → **换串口端口绕开可疑引脚**（见下节，本工程已内置该能力）；
> ④ 换 CP2102 的另一侧 USB 口（无源 hub 会导致 COM 口时有时无）；
> ⑤ 用 DTR 复位后再抓（板子自检跑完后停在 `for(;;)`，不复位可能抓不到窗口）。
>
> **抓取脚本**（含 DTR 自动复位，比串口助手可靠；本项目用它在取 RESULT 行）：
> ```bash
> python scripts/capture_board.py COM3 115200 30 --out board_opt.log
> ```
> 它会自动把 RESULT 行解析成可回填格式，见 `scripts/capture_board.py`。

> **推荐的自动板测方式（不依赖长串口日志）**：正式测量固件会把 KAT、熵源状态和
> 10 项 cycles 写入 `smc_board_results` RAM 结果块；脚本从 ELF 符号表自动定位地址，
> 烧录后轮询到 `state=DONE` 才输出结果：
> ```powershell
> python scripts\board_bench.py embedded\cortex-m3\smc_m3_mcu.elf `
>   --timeout 300 --json bin\board_mcu.json
> # 只读取当前板内已完成的结果，不重烧：
> python scripts\board_bench.py embedded\cortex-m3\smc_m3_mcu.elf --no-flash
> # 生成 REF/OPT/TINY/MCU 对比表：
> python scripts\compare_board_bench.py bin\board_ref.json bin\board_opt.json `
>   bin\board_tiny.json bin\board_mcu.json --out bin\board_compare.md
> ```
> 该路径由 ST-Link 读取 RAM，适合竞赛报告采数；串口保留用于现场演示和人工观察。

### 2.2.1 换串口端口（绕开可疑引脚）

固件默认输出到 **USART1：PA9=TX / PA10=RX**。若该组引脚在你的板子上
被占用、走线断、或排针位置不好找，可编译期切到 USART2/USART3：

| 构建命令 | 输出引脚 | CP2102 接线 |
|---|---|---|
| `bash build.sh flash opt`（默认） | **PA9=TX / PA10=RX** | TX→PA10，RX→PA9 |
| `bash build.sh flash opt uart2` | PA2=TX / PA3=RX | TX→PA3，RX→PA2 |
| `bash build.sh flash opt uart3` | PB10=TX / PB11=RX | TX→PB11，RX→PB10 |

```bash
# 例：烧 USART3 版本
bash build.sh flash opt uart3
pyocd flash -M under-reset -f 100k -t stm32f103rc -e chip smc_m3_opt_uart3.elf
python ../scripts/capture_board.py COM3 115200 30
```

> 该开关的实现见 `embedded/port/smc_port_f1.c` 的 `SMC_UART_PORT` 宏块
> （波特率逻辑不变，只换 GPIO 配置分支）。代价：Flash **+8 字节**（33 520 → 33 528）。
> 三个端口的寄存器在 `stm32f1xx_min.h` 里都已定义好。

### 2.2.2 串口无输出时的判定树（2026-10-16 实测整理）

已确认排除的项（别重复走这些弯路）：

| 排除项 | 验证方式 | 结果 |
|---|---|---|
| 驱动没装 | `ProblemCode=0  Service=silabser`，COM3 出现 | ✅ 已排除 |
| 固件没烧进去 | `pyocd flash` 报 `skipped N bytes` | ✅ 已排除 |
| 芯片是克隆片 / 有读保护 | DP IDR=0x1ba01477、Cortex-M3 r1p1、ROM table 正常 | ✅ 已排除 |
| USART 没初始化 | 核对 `GPIOA_CRH`：PA9=0xB（TX 复用推挽）、PA10=0x4（RX 浮空输入），`BRR=69`、`CR1=0x200C` | 修复后重新验证 |
| GPIO 复用没使能 AFIO | 同上，代码已 `RCC->APB2ENR \|= AFIOEN` | ✅ 已排除 |

修复并重新烧录后，再检查物理接线：TX/RX 是否交叉、是否接到了正确的针脚。
此时最有效的动作是**换端口**（§2.2.1）——用 PB10/PB11 试，能立刻区分
「是 PA9/PA10 这组脚的问题」还是「整体接线思路的问题」。

### 2.2.3 诊断固件 `uart_probe`（判断「固件跑没跑」的最快手段）

当上面所有软件侧手段都用尽了仍无输出时，用这个固件把问题一刀切开：

```bash
cd embedded/cortex-m3
bash build.sh uart_probe flash
pyocd flash -M under-reset -f 100k -t stm32f103rc -e chip smc_m3_uart_probe.elf
```

它只有 14.5 KB，**不含任何算法、不含 printf、不含随机数**，
同时做三件事：

| 观测点 | 含义 |
|---|---|
| **PA5 板载 LED 以约 2 Hz 闪烁** | 固件正在跑（肉眼可见，无需任何软件） |
| USART1(PA9=TX) 持续输出 `U1=UART1_PA9` / `1` / `3` | PA9/PB10 这组引脚通 |
| USART3(PB10=TX) 持续输出 `U3=UART3_PB10` | 同上 |

**判定树**：

| 现象 | 结论 | 下一步 |
|---|---|---|
| LED 闪 + 串口无输出 | 固件在运行，UART 配置或物理链路异常 | 先核对 CRH/RX 模式，再检查 TX/RX 与共地 |
| LED 不闪 | **固件没跑起来** | 查 BOOT0 是否拨到高电平（ISP 模式）、复位电路、Flash 是否真写入 |
| LED 闪 + 输出乱码 | 波特率不对 | 试 9600/38400 |

> **本项目实测（2026-10-16）**：最初正式固件与诊断固件都无串口输出，根因不是接线，
> 而是 PA9/PA10 错写 `GPIOA_CRL`（应为 `CRH`），且 RX 被误配成复用推挽输出。
> 修复后诊断固件在 COM3 连续收到 `11111111`，正式 OPT 固件经 SWD 读取
> `g_fail=0`，确认自检完整通过。以后遇到同类现象不能仅凭“烧录成功”排除软件配置。
> 诊断完成后烧回正式固件：
> ```bash
> pyocd flash -M under-reset -f 100k -t stm32f103rc -e chip smc_m3_opt.elf
> ```

### 2.3 烧录器认不到芯片时

地阔星 F103C8T6 有时需要「连接复位」才能进 SWD：

```bash
pyocd flash --connect-under-reset smc_m3_opt.elf
# 或手动：按住 RESET 点一下，出现"Port:0"后再放开
```

## 3. 构建与烧录

```bash
export PATH="$PATH:/c/Program Files (x86)/Arm GNU Toolchain arm-none-eabi/14.2 rel1/bin"
cd embedded/cortex-m3

# 默认：OPT 内核（Flash 33.5KB / RAM 13.7KB）
bash build.sh flash opt

# 内核 A/B（回答"优化在 MCU 上到底有没有收益"，见 §8）
bash build.sh flash ref        # Flash 27.7KB（无 comb 表）
bash build.sh flash opt

# 常量时间
bash build.sh flash opt ct

# 功耗测量用（连续运算循环，占空比≈100%）
bash build.sh flash opt loop
bash build.sh flash opt loop_verify

# 32KB 适配证明
bash build.sh 32k min         # Flash 29.5KB —— 链接成功即证明
```

烧录（**本机 2026-10-14 实测通过的命令**）：

```bash
# ✅ 实测可用：全片擦除 + 连接复位 + 降速 + 正确目标名
pyocd flash -M under-reset -f 100k -t stm32f103rc -e chip smc_m3_opt.elf
# 实测输出：Erased chip, programmed 34816 bytes (17 pages) at 4.91 kB/s

# 或 OpenOCD
openocd -f interface/stlink.cfg -f target/stf1x.cfg \
        -c "program smc_m3_opt.elf verify reset exit"
```

> **⚠ 关键：`-e chip` 不是可选项，是本工程的必需项**
>
> 实测踩坑：省略 `-e chip`（即默认 `-e sector`）时，
> 报 `flash program page failure (address 0x08000000; result code 0x1)`——
> **芯片能读到、CPU 核识别正确（Cortex-M3 r1p1），但擦除/写入失败**。
> 加 `-e chip`（全片擦除）立刻成功。
>
> 为什么会这样：`-e sector` 只擦目标扇区，而地阔星 F103C8T6 出厂 Flash 常带
> **读保护(RDP) 或厂商 bootloader 占用了低地址扇区**，导致部分页擦除失败。
> 全片擦会一并清掉这些状态。代价是每次烧录慢约 3 秒，但**成功率 100%**。
>
> 验证写入成功的标志（跑第二次）：
> `skipped 34816 bytes (17 pages)` —— 表示 Flash 内容与固件**已完全一致**。

> **pyocd 参数速查（本机 2026-10-14 实测踩过的坑）**：
>
> | 目的 | 正确参数 | 常见错误写法 / 症状 |
> |---|---|---|
> | 连接复位（地阔星 F103 必需） | `-M under-reset` | `--connect-under-reset`（新版已删，报 unrecognized） |
> | 指定目标芯片 | `-t stm32f103rc` | `stm32f103rb`（报 target type not recognized） |
> | 降SWD 速率 | `-f 100k` | 默认 1MHz 易失败 |
> | **全片擦除（必需）** | **`-e chip`** | **省略 → `flash program page failure result 0x1`** |
> | 探测连接 | 无 `probe` 子命令 | `pyocd probe`（新版已移除） |
>
> **`STLink error (9): Get IDCODE error` 排查**：ST-Link 本身正常（`pyocd list` 能列出），
> 但**读不到目标芯片** → 板子没上电或 SWD 线没接全。按序检查：
> ① 板子**是否上电**（此时若 CP2102 驱动已装，会立刻出现 COM 口作为判据）；
> ② `SWDIO / SWCLK / GND` 三根都接（**GND 最易漏**）；
> ③ 加 `-f 100k` 降速；
> ④ 加 `-M under-reset`；
> ⑤ 按住板上 **BOOT0** 拨到高电平再上电（进 ISP 模式），烧完拨回。

> ⚠ **`-specs=nano.specs` 必须在链接命令里**（build.sh 已放）。  
> 实测：只在编译阶段给 specs 时链接仍拉完整版 libc.a，产物 50KB；  
> 补到链接命令后降到 33.5KB —— 差 16.5KB。这是 F103 移植最大的一个坑。

## 4. 已实测的尺寸数据（可直接写入报告）

> 环境：GNU Arm 14.2.Rel1，`-O2 -specs=nano.specs`，STM32F103C8T6（64KB Flash / 20KB RAM）  
> 口径：`text` ≈ Flash 占用（= `arm-none-eabi-size` 的 text），`data+bss` ≈ 静态 RAM 占用。  
> **这些是链接器实测值，不是估算**，可直接回填 `docs/04 §5`。

| 配置             | 内核                   | Flash(text) | data | bss    | RAM 合计    | 装进 64K? | 装进 32K?    |
| -------------- | -------------------- | ----------- | ---- | ------ | --------- | ------- | ---------- |
| `flash ref`    | REF 教科书基线            | 27 696      | 460  | 9 116  | 9 576     | ✅       | —          |
| `flash opt`    | OPT（含 comb 表，默认）     | 33 520      | 460  | 13 220 | 13 680    | ✅       | —          |
| `flash opt ct` | OPT + 常量时间           | 33 024      | 460  | 13 220 | 13 680    | ✅       | —          |
| `flash tiny`   | TINY+SMALL           | 33 152      | 460  | 9 116  | 9 576     | ✅       | —          |
| `flash min`    | 最小裁剪（关 CBC/ENC/comb） | 30 112      | 460  | 9 116  | 9 576     | ✅       | —          |
| **`32k min`**  | **最小裁剪 + 32K 约束**    | **29 552**  | 460  | 9 116  | **9 576** | ✅       | ✅ **链接成功** |

**三条可直接写进报告的结论**：

1. **「适配 <32KB Flash」已被链接器证明**：`32k min` 配置 text = **29 552 B < 32 768 B**，  
   且用了 32KB 约束链接脚本（`stm32f103c8_32k.ld`）——这是**可复现、零成本**的证据  
   （不需要买小 Flash 板子，见 `docs/05 §3.2`）。
2. **RAM 侧同样宽裕**：最小配置静态 RAM 仅 **9 576 B < 20 KB**，  
   剩余约 10 KB 可留给 DTLCP 上下文与任务栈。
3. **⚠ 一个反直觉但重要的实测结论**：**REF 内核比 OPT 更小**（27.7 KB vs 33.5 KB）。  
   原因是 OPT 的两个优化都要付 Flash 代价——  
   基点 comb 表 2 048 B 常量（占 Flash）+ SM4 T-table 4 128 B（占 bss）；  
   而 REF 用纯代码实现，不含这些表。  
   **因此"优化"在 MCU 上的正确表述是「用 Flash/RAM 换时间」**：  
   若 Flash 紧张选 REF/tiny/min，若要性能选 OPT/tiny。  
   这条必须写进报告，否则评审会问"为什么优化后代码变大了"。

> `tiny` 档的 bss 只有 9 116 B（比 opt 少 4 104 B），因为 SM4 SMALL 内核用  
> 256 B S-box 替代了 4 KB T-table —— 这&#x662F;**"轻量化裁剪"最直接的内存证据**。

## 5. ⚠ 熵源：无硬件 RNG 的处理（如实说明）

STM32F103C8T6 **没有 RNG 外设**（ST 官方特性表：只有 CRC + 96 位 UID）。  
`smc_port_f1.c` 的处理是：**ADC1_IN0(PA0) 采样噪声 → LFSR 白化 → 健康门禁**。

```
熵源质量边界（务必如实写进报告，不要含糊）
─────────────────────────────────────────────
✗ 不是 TRNG。ADC 噪声的熵质量远低于硬件 TRNG，
  不满足 GM/T 随机数检测完整项，也不满足 FIPS 140-2 对 entropy source 的要求。
✓ 只满足两件事：
  1) docs/03 §2.4「实验室/非生产允许确定性 nonce」的**下限之上**；
  2) 自检里可观测的行为：两次 keygen 生成的公钥**确实不同**（不是固定种子）。
→ 生产部署**必须**改接外部 TRNG 芯片（如 ATECC608 / SGS8706）。
```

自检四项（返回码见串口输出）：

| 返回码 | 含义                                          |
| --- | ------------------------------------------- |
| 0   | 通过：ADC 无超时、40 样本互不重复、比特 1∈[35%,65%]、8 窗口内唯一 |
| -2  | ADC 采样超时（检查 PA0 是否引出、ADC 时钟是否使能）            |
| -4  | 全局样本重复（外设卡死/引脚悬空）                           |
| -5  | 比特失衡（熵质量差，改用外部 TRNG）                        |
| -6  | 窗口内重复（低熵，建议换熵源）                             |

> ⚠ **措辞纪律**：板级自检里这一项叫「熵源自检」，**不叫「TRNG 健康自检」**——  
> 后者是虚假陈述，评审追问会很难答。代码里已按此措辞（见 `board_selftest.c`）。

### 6.1 量级合理性自查（与 M4 同口径，M3 预期更低）

| RESULT 键      | host 参考 cycles/op | M3 预期量级   | 8MHz 单次时间量级 |
| ------------- | ----------------- | --------- | ----------- |
| sm3_1KB       | ~4 930 (OPT)      | 1–3 万     | 0.1–0.4 s   |
| sm4_ecb_block | ~145 (OPT)        | 0.3–0.9 千 | 40–110 µs   |
| sm2_keygen    | ~428 748          | 100–300 万 | 0.1–0.4 s   |
| sm2_sign      | ~508 454          | 120–350 万 | 0.15–0.45 s |
| sm2_verify    | ~1 341 441        | 300–900 万 | 0.4–1.1 s   |
| sm2_ecdh      | ~1 072 265        | 250–700 万 | 0.3–0.9 s   |

> 若某行是上表的 1/10 或 10×：先怀疑时钟口径（8MHz vs 72MHz）而不是算法。  
> 若 SM2 全部为 0：DWT 未使能（`smc_port_init()` 没跑）。

### 6.2 想跑 72 MHz（可选）

地阔星 F103C8T6 板载 **8 MHz 晶振**，配 PLL 到 72MHz 能快 9 倍：

1. 在 `smc_port_f1.c` 的 `smc_port_init()` 里加 HSE + PLL 配置（`RCC->CFGR`）；
2. 构建时加 `-DSMC_CPU_HZ=72000000`；
3. **不配 PLL 也能出数据** —— cycles 与主频无关，只影响 µs 换算与功耗折算。  
   赶时间就先别配，报告里写明"HSI 8MHz"即可。

## 7. W5500（MCU 侧 DTLCP 真机已跑通）

`docs/07` 的 T4 任务。已购 W5500 的接法：

| W5500     | F103C8T6         |
| --------- | ---------------- |
| SCK       | PA5（SPI1_SCK）    |

驱动已按 WIZnet 官方 ioLibrary 的 VDM SPI 和 socket 指针流程核对，并通过 ARM `-Wall -Wextra`
交叉编译。探针会自动尝试 PB10 与 PA4 两种常见 SCS 接法，并把原始寄存器写入 SWD 结果块。
**2026-10-16 首次实物探测曾读回全 0；修正接线后 VERSIONR=0x04、PHY Link=1，
PC 协商 100 Mbps，36 B UDP 回显逐字节一致。随后 FULL/RESUME/PSK/PSK 0-RTT 四模式
全部完成真机加密遥测 ACK，数据见 `docs/04 §6.3`。**

> 裸机 `_estack` 在链接脚本里设于 RAM 顶（`ORIGIN+LENGTH`），

> 运行时栈与静态区共用同一块 RAM，不能把两者分别按 20 KB 计算。
>
> **缓冲复用后的握手栈（ARM M3 ABI 实测）**：
>
> | 内部函数            | 自身帧 |
> | ------------------ | ----: |
> | `server_full`      | 496 B |

> | `server_resume`    | 472 B |
> | `server_psk`       | 464 B |

## 9. 功耗测量（无 INA226 时的可行方案）

你手上没有 INA226（`docs/05` 列为待购）。三条替代路径，按可行性排序：

| 方案               | 做法                                                                                   | 精度           | 成本    |
| ---------------- | ------------------------------------------------------------------------------------ | ------------ | ----- |
| **A. 借万用表 mA 档** | 5V 充电宝 → 万用表 mA 档 → 板子 VCC；测 `flash opt loop`（连续签名）与 `flash opt`（空转）两次的平均电流，差值法算单次能量 | 中（人工读数、内阻压降） | ¥0    |
| B. 买 INA226 模块   | 按 `docs/08 §6` 接，注意自身 330 µA 要接在分流电阻之前                                               | 高            | ¥7–20 |
| C. 只报模型估算        | 保留 `docs/04 §6` 的能量模型，报告里明确标注「估算」                                                    | 低            | ¥0    |

**建议**：时间够就 A（半天能出数），否则如实保留估算。  
**不要**在报告里把估算写成实测。

差值法公式（与 `docs/08 §6` 相同）：


```
I_crypto(µA) = I_loop − I_idle
T_op(s)      = cycles_per_op / f_clk        # f_clk = 8e6（本骨架默认）
E_op(µJ)     = V(V) × I_crypto(µA) × T_op(s) × 1e-3
```

## 10. 常见问题排查

| 现象 | 原因与处理 |
|---|---|
| 串口无输出 | ①TX/RX 接反（CP2102 TX→PA10、RX→PA9）；②不是 115200；③板子没跑（先量 3V3）；④CP2102 驱动没装（去 silabs 官网装） |
| 输出乱码 | 波特率不匹配；或串口工具把 UTF-8 当 GBK 显示（中文乱码不影响数字） |
| ST-Link 认不到芯片 | 地阔星 F103 常需 `--connect-under-reset`，或按住 RESET 点一下；也可能是买到克隆片 |
| 一上电就停住/反复重启 | HardFault，多为时钟配置错误——**先回到不配 PLL 的 8MHz 版本** |
| `两次生成公钥不同` 失败 | ADC 噪声没工作：确认 PA0 引出、ADC 已使能（`smc_port_init` 会调 `adc_init`）；或按 §5 表格看返回码 |
| 熵源自检返回 -2 | ADC 采样超时：PA0 悬空或 ADC 时钟未使能 |
| 熵源自检返回 -4/-6 | 样本重复/低熵：PA0 接地或接了固定电压源；改接悬空脚或加噪声源 |
| cycles 全是 0 | DWT 未使能：确认 `smc_port_init()` 被调用（`main()` 第一句） |
| 链接报 `undefined reference to _sbrk` | newlib 系统调用桩缺失，见 `main.c` 末尾（已自带，检查是否被误删） |
| 链接报 `region FLASH overflowed` | 用了 `opt` 配置 + 32K 约束；改用 `32k min`，或去掉 `-DSMC_SM2_FIXED_TABLE` |
| ELF 是 0 字节 | 向量表被优化掉了：`g_vectors` 需要 `__attribute__((used))`（本工程已加） |

## 12. 移植中踩过的坑（已修，供二次开发参考）

| # | 坑 | 症状 | 修法 |
|---|---|---|---|
| 1 | `-specs=nano.specs` 只加在**编译**阶段 | 链接仍拉完整版 `libc.a`，Flash 50KB，32K 直接溢出 | 必须也加到**链接**命令（build.sh 已处理，差 16.5KB） |

| 4 | newlib 系统调用桩缺失 | `undefined reference to _sbrk/_lseek/_fstat/...` | `main.c` 末尾给全套最小桩；`_sbrk` 返回失败（强制零动态内存） |
| 5 | `.._.._x.o` 目标文件名 | Git Bash 下被当隐藏文件，`*.o` 通配匹配不到 → 链接出空 | 规范化路径前缀，并**显式收集 OBJS 列表**代替通配 |
| 6 | UTF-8 中文 banner | 每字 3 字节，全套 banner ~1.5KB，32K 装不下 | 32K 模式自动加 `-DSMC_BOARD_TINY_PRINT=1`（换英文短标签，判定逻辑不变） |
| 7 | `stack_depth.py` 不认 ARM | 只匹配 x86 的 `callq`，ARM 是 `bl <sym>` → 调用图全空、栈深被低估 | 正则加 `bl|blx`，`--objdump` 参数化，空输出视为失败 |
| 8 | `stack_depth.py` 的 memo 污染 | 递归保护残缺值被缓存，最长路径退化成单节点 | 只在 guard 为空时写 memo（x86 下恰好没触发，ARM 上暴露） |

| 10 | F1 GPIO 是 CRL/CRH | F4 的 `MODER/AFR[]` 在 F1 不存在；且**必须先使能 AFIO 时钟** | 见 `stm32f1xx_min.h` 注释 |

| MCU | `-mcpu=cortex-m4 -mfpu=fpv4-sp-d16 -mfloat-abi=hard` | `-mcpu=cortex-m3 -mthumb`（**无 FPU**） |
| 默认主频 | HSI 16MHz | HSI **8MHz** |
| GPIO | `MODER/OTYPER/AFR[]` | `CRL/CRH`，**需先使能 AFIO** |
| 寄存器头 | `stm32f4xx_min.h` | `stm32f1xx_min.h`（RCC 结构体化） |
| 端口层 | `port/smc_port_stm32.c`（读 `RNG->DR`） | `port/smc_port_f1.c`（**ADC 噪声 + 白化**） |
| 链接脚本 | `stm32f407.ld`（1M/128K） | `stm32f103c8.ld`（**64K/20K**）+ `_32k` 变体 |
| libc | 默认 | **`-specs=nano.specs` + `-u _printf_float`（链接阶段必须）** |
| FPU 使能 | `SCB_CPACR` 开 FPU | **无**（M3 无 FPU，不要照抄） |
| DWT/CYCCNT | ✅ | ✅ **同样可用** → cycles 实测不受影响 |
| 32K 适配证明 | 未做 | ✅ 已做：`32k min` = 29 552 B |
