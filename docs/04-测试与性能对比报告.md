# 04 · 测试与性能对比报告

> 选题：资源受限物联网终端轻量级国密算法优化与 DTLCP 国密改造实现（A1-33）
>
> **本文全部数据取自同一次测量快照（2026-10-09）**，原始输出见 `bin/bench_results.md`（算法基准）、
> `bin/size_report.md`（内存/栈深）；协议数据由 `scripts/demo_run.sh` 实测。功耗为能量模型估算，已逐处标注。

## 1. 测试环境与方法

### 1.1 环境

| 项 | 版本 / 取值 |
|---|---|
| 主机 | x86-64 Windows（win32 10.0） |
| 编译器 | gcc 8.1.0（MinGW-W64），`-std=c99 -O2 -Wall -Wextra` |
| 交叉验证 | OpenSSL 3.2.4 CLI |
| 估算脚本 | Python 3.13.5（`scripts/power_model.py`） |
| 计时 | RDTSC 读取 CPU 周期（cycles）＋高精度计时（换算 µs） |

### 1.2 测评口径（**重要**）

- **算力**：x86-64 实测 cycles/操作；同机、同迭代次数、同 API，直接可比。
- **比值优先于绝对值**：RDTSC 计数受 CPU 频率状态影响，**跨运行绝对值不可比**。
  因此所有加速比都在**同一次基准输出内**计算（同一进程连续测量）。
  *实测验证*：同一构建连续运行 4 次，SM4 ECB 比值 1.81–1.93×、CBC 1.92–1.99×、
  SM3 0.915–0.919×，**会话内比值稳定（±5%）**；但**跨会话**比值仍有系统性偏差
  （早期快照曾给出 SM4 ECB 1.48×、verify 1.93×——同一份代码，仅主机频率状态不同）。
  故本报告一律以**本文快照内的比值**为准，历史快照数字已作废。
- **单项优化用 A/B 变体隔离**：新增 `notab` 构建（与 `opt` 同内核，仅关闭 SM2 基点 comb 表），
  使"comb 的净收益"可在同一次输出内直接相除，不受跨会话偏差影响。
- **内存**：`size` 统计对象文件，text≈Flash 占用，data+bss≈RAM 静态占用。
- **栈深**：`-fstack-usage` 只给**单函数自身帧**，本报告另用 `scripts/stack_depth.py`
  （`.su` 帧 + objdump 调用图）计算**最长加权调用路径**——这是任务栈预算的真正依据。
- **功耗**：参数化能量模型（默认 Cortex-M4 典型参数），**模型估算而非实测**。
- **协议开销**：`scripts/demo_run.sh` 在 UDP 127.0.0.1 环回实测握手字节、SM2 运算次数与时延。

### 1.3 内核变体定义（`scripts/build.sh`）

|---|---|---|---|---|
| ref | REF | REF | REF | — |

### 2.2 基点 comb 预计算表的三重校验

`k·G` 的优化（comb 查表）不改变任何输出，由三道独立关卡保证：

1. **生成时自检**（生成器内）：全部 31 个非占位表项在曲线上；16 个随机标量下
   comb 组合结果 == REF 二进制倍点-点加结果（逐位）。
2. **来源独立**：`B_i = 2^(i·d)·G` 由**反复倍点**算出（不经过标量乘），避免"用被优化的算法验证自己"。
3. **差分指纹**：指纹输入包含 `sm2_keygen` / `sm2_sign_with_k` / `sm2_verify` / `sm2_ecdh`，
   而 `opt` 变体的 keygen 与 sign 正是走 comb 路径——指纹与 REF、与 `notab` 三者逐位相同（§2.1）。
4. **CI 一致性断言**：`scripts/gen_fixed_base.sh --check` 校验仓库内表与生成器同步，防止表过期或被手工改动。

## 3. 算法性能对比（x86-64 实测，比值 = REF cycles ÷ 对应内核 cycles，>1 表示更快）

### 3.1 SM3 哈希

| 操作 | REF | FAST(opt) | TINY | FAST/REF | TINY/REF |
|---|---|---|---|---|---|
| hash 1KB | 9147 | 9960 | 9801 | 0.92× | 0.93× |
| hash 4KB | 35154 | 38408 | 37741 | 0.92× | 0.93× |
| HMAC-SM3 (256B) | 4748 | 5029 | 4825 | 0.94× | 0.98× |

**如实结论：SM3 的"展开/批量"优化在 x86-64 上不产生收益，反而慢 6–8%。**
原因：`-O2` 已对基线循环做充分调度与展开，手工展开限制了编译器自由度。该内核的价值在**内存侧**
（TINY 的 16 字滚动调度把单函数帧压到 64 B）与**顺序执行的 MCU**（无乱序执行、无硬件除法），
但后者**尚无板上数据**（见 §7 待办）。**本报告不把 SM3 计入性能收益项**，且该结论与
第三方对照一致：对 GmSSL 我们同样慢 0.87×（§4）。

|---|---|---|---|---|---|

### 3.4 域算术 Fp（**根因定位**）

> **本表数字取自交错测量**（`bin/thirdparty_compare.md` 的域算术节：两侧二进制交替运行、各取多轮最小值），
> 而非顺序快照。原因：REF 与 OPT 的 `fe_mul` 差值只有约 5%（<10%），
> **顺序运行会出现离群值**——顺序快照曾给出 `REF 677 / OPT 561`（与"OPT 略慢"矛盾），
> 而 5 轮交替测量稳定为 `REF 533–539 / OPT 561–569`。此类小差值必须交错测量才可信。

| 操作 | REF | OPT | OPT/REF |
|---|---|---|---|
| fe_mul | 533 | 561 | **0.95×** |
| fe_sqr | 574 | 519 | 1.11× |
| fe_inv | ~204,000 | ~191,000 | 1.06× |

**这是一处必须如实报告的反直觉结果**：域乘法上 **OPT 反而略慢于 REF**（561 vs 533）。
即 8×8 展开乘法的收益，被 Solinas 折叠约减（多轮折叠 + 试商收尾）的成本吃掉了，净效果为负。
这修正了 docs/02 早期"折叠约减是纯收益"的表述——它消除了**除法依赖**（对无硬件除法的 MCU 有理论价值），
但在有硬件除法的 x86-64 上并不划算。该结论同时也是 §4 第三方对照中"变基点落后"的直接原因。

> **方法学提示**：`bench_results.md` 的 `fe_*` 行来自顺序运行（ref → opt → notab → tiny），
> 适合看数量级；**做 5% 量级的 REF/OPT 判定请用交错测量**——`scripts/thirdparty_bench.sh`
> 同时输出两侧的 `fe_*` 对照列，可直接引用。

### 3.5 结果解读

- **基点 comb 表是本轮最大单项收益**：keygen 的标量乘由约 257 次倍点降为 **51 次倍点 + ≤51 次混合加**，
  使 keygen/sign 再快 **2.63× / 2.31×**。`notab` 列证明该优化**只**作用于基点乘。
- **verify / ecdh 不受 comb 影响（1.01×，噪声内）**——设计使然：二者是**变基点**运算
  （`sG + tP` 与 `k·P_peer`），无预计算表可用。verify 已由交织双标量乘优化到 2.32×。
- **域运算是当前最大瓶颈**（见 §3.4 与 §4）：标量乘算法的优势与域运算的劣势在变基点上相互抵消。
- **SM4**：T-table 的 1.8–2.1× 与 SM2 的优化互相独立，共同构成端到端收益。

## 4. 第三方基线对照（**外部锚点，GmSSL 3.1.1**）

本仓库原有的全部加速比都是"本库 REF vs 本库 OPT"——**自己比自己**，对评审不具可比性。
为此增加第三方对照：**GmSSL 3.1.1**（国内事实上的国密参考实现，且同为**可移植 C**，
比 OpenSSL 的手写汇编更适合与 MCU 取向的实现对比）。

> 生成方式：`bash scripts/thirdparty_bench.sh`（可复现，自动下载/编译 GmSSL 子集并交错测量）；
> 原始报告：`bin/thirdparty_compare.md`。测量：3 轮交错运行两侧二进制，每侧取最小值。
> 加速比 = **GmSSL cycles ÷ 本库 opt cycles**，>1 表示本库更快。
> 两侧均为 `-O2` 单线程、纯 C（未编入 GmSSL 的 `sm3_x8_avx2`/`sm4_aesni_avx` 汇编路径）。

| 类别 | 操作 | GmSSL 3.1.1 | 本库 opt | 本库 / GmSSL |
|---|---|---|---|---|
| SM3 | hash 1KB | 8,596 | 9,867 | 0.87×（**本库慢**） |
| SM3 | hash 4KB | 33,621 | 38,556 | 0.87×（**本库慢**） |
| SM3 | HMAC-SM3 256B | 4,429 | 5,058 | 0.88×（**本库慢**） |
| SM4 | ECB 单块 | 227 | 203 | **1.12×**（本库快） |
| SM4 | CBC 1KB | 18,978 | 18,112 | 1.05×（本库快） |
| SM4 | CTR 1KB | 18,976 | 17,790 | **1.07×**（本库快） |
| SM2 | 基点乘 k·G | 1,337,232 | 832,206 | **1.61×**（本库快） |
| SM2 | **变基点乘 k·P** | 1,308,039 | 2,109,850 | **0.62×（本库慢）** |
| SM2 | 签名 | 2,117,211 | 1,025,323 | **2.06×**（本库快，见注） |
| SM2 | 验签 | 2,753,821 | 2,663,708 | 1.03×（持平） |
| Fp | **域乘法** | 254 | 561 | **0.45×（本库慢 2.2×）** |
| Fp | 域平方 | 255 | 519 | 0.49×（**本库慢 2.0×**） |
| Fp | 域求逆 | 94,310 | 195,409 | 0.48×（**本库慢 2.1×**） |

### 4.1 结论（诚实版）

1. **SM4 与 GmSSL 打平或略胜**（1.05–1.12×）——对一个"资源受限取向"的实现，这是很好的位置。
2. **SM2 基点乘快 1.61×**：因为本库有 comb 预计算表，而 GmSSL **不做**定点特化
   （其 `point_mul_generator` 与 `point_mul` 耗时几乎相同：1,337,232 vs 1,308,039）。
   这是 comb 优化最有说服力的外部证据——它不是"相对自己基线"的数字游戏。
3. **验签持平**（1.03×）：两边都是"两次标量乘 + 一点加"，本库的交织共享倍点与 GmSSL 的
   域运算优势相互抵消。
4. **变基点乘慢 0.62×**，根因**已定位到域运算**：本库 `fe_mul` 慢 **2.2×**（561 vs 254）。
   把点运算次数折算进去后可以完全解释：变基点两边倍点次数几乎相同（各约 256 次），
   因此差异只能来自单次域运算成本。
5. **SM3 慢 0.87×**：与 §3.1 一致——本库 SM3 在 host 上没有优势可言，不做辩解。
6. **签名 2.06× 含口径差异**：GmSSL 的 `sm2_do_sign` 每次向**系统 CSPRNG** 取 k，
   该开销已单列为 **451,878 cycles（135.6 µs）**；本库用 HMAC-SM3 派生 nonce（无系统调用）。
   扣除熵源后为 (2,117,211−451,878)/1,025,323 = **1.62×**——这才是纯签名运算的可比数值。

### 4.2 由此得到的优化排序（本轮明确）

**域运算（`fe_mul`/`fe_sqr`/`fe_inv`）是当前第一瓶颈，且收益覆盖全算法。**
GmSSL 的 `fe_mul` 用一次性的、硬编码 Solinas 归约（`r[i] = s[i] + s[8..15]` 的组合，无试商收尾），
而本库走"多轮折叠 + 试商收尾 + 两次条件减"。改造方向明确：
把归约改写为**一次到位**的形式（或改用 Montgomery 域），预期可把 `fe_mul` 从 561 拉近 254–300，
从而同时改善变基点乘（0.62×→有望 >1×）、验签与基点乘。
**这比继续在标量乘算法上做文章的收益大得多**——标量乘算法已经比 GmSSL 更好，短板在底层。

## 5. 内存占用与裁剪对比

gcc -O2 对象文件实测（text≈Flash，data+bss≈RAM）：

| 配置 | 内容 | text (B) | data | bss | 最大调用路径栈深 |
|---|---|---|---|---|---|
| full | 默认（SM3/SM4=FAST，含 comb 表） | 26572 | 0 | 4128 | 3280 B |
| **no-comb** | 同 full，`SMC_SM2_FIXED_TABLE=0` | **23476** | 0 | 4128 | 3280 B |
| trim-noenc | 裁 SM2 公钥加密/解密 | 24836 | 0 | 4128 | 3280 B |
| **trim-min** | SMALL+TINY + 裁 ENC/CBC + 关 comb | **20864** | 0 | **0** | 3280 B |
| tiny-stack | 全功能 + SM3 TINY | 26588 | 0 | 4128 | 3280 B |
| ct-const | `SMC_SM2_CT=1`（comb 自动禁用） | 21288 | 0 | 4128 | **3440 B** |

要点：

- **comb 的代价 = 3096 B Flash，RAM 增量 0**：其中表本体 2048 B（`static const`，进 `.rdata`
  计入 text 列）＋ comb 代码 1048 B。因为代价落在 Flash 而非 RAM，对"RAM 紧张"的 MCU 是净赚
  （`full` 与 `no-comb` 的 bss 完全相同：4128 B）。
- **RAM 归零的两条路径**：SM4 的 SMALL 内核去掉 4 KB T-table（4128→0）；
  `SMC_SM2_FIXED_TABLE=0` 是**新增的第三条"闪存换速度"开关**。
- **模块构成（full）**：sm3 1664 / sm4 2104 / sm2_arith 16976 / sm2 4152 / hmac_sm3 856 / smc_rng 820 B。
- **常量时间构建反而略省 Flash**（21288 < 23476）：`SMC_SM2_CT=1` 下 wNAF/交织代码整体不编译。
- **`<32KB Flash` 约束**：`trim-min` 20864 B 满足，且自带 RAM 0。

### 5.1 栈深：修正一处早期错误结论

早期文档称"栈预算以 `fe_pow_mod` 688 B 为首要预留"——**该结论不成立**。
`-fstack-usage` 给的是**单函数自身帧**，而任务栈需要的是调用链之和。
`scripts/stack_depth.py`（`.su` + objdump 调用图）计算结果：

| 指标 | 默认（full） | 常量时间（ct-const） |
|---|---|---|
| 最大**单函数**帧 | `scalarmult_add_naf` 1792 B | `scalarmult_add_naf` 1792 B |
| **最大调用路径**栈深（下界） | **3280 B** | **3440 B** |
| 建议任务栈（1.5× 余量） | **≥ 5 KB** | **≥ 6 KB** |

最长路径：`scalarmult_add_naf(1792) → build_odd_table(448) → sm2_jac_add(624) → sm2_fp_mul(368) → fe_mod_once(48)`。

> 口径：权重为各函数自身静态帧之和，**不含**返回地址/寄存器保存等 ABI 开销，
> 且函数指针间接调用不在图中——故为上界估算的**下界**，实机移植须留安全余量。
> 注：`fe_pow_mod`（Fermat 求逆，688 B）不再是最大热点（现列为第 3 位）。

## 6. DTLCP 协议开销对比

UDP 127.0.0.1 环回实测：

| 模式 | 握手航班 | SM2 运算 | 握手线上字节 | 握手时延 |
|---|---|---|---|---|
| FULL（ECDHE+SM2 双向认证） | 3 flights ≈ 1.5-RTT | 5 次（2×临时密钥＋签名＋验签＋ECDH） | 1198 B（604＋594） | **4.00 ms** |
| RESUME（会话恢复） | 2 flights ≈ 1-RTT | 0 | 428 B（222＋206） | ≈1.0 ms |
| PSK（预共享密钥 + 0-RTT） | 1 flight | 0 | 474 B（276＋198） | ≈1.0 ms |

### 6.1 comb 对握手时延的端到端贡献（同条件 A/B）

FULL 的 5 次 SM2 中，**2 次临时密钥生成（`eph_keygen` 走 `sm2_scalarmult_base`）与 1 次签名**
落在 comb 快路径上，验签与 ECDH 为变基点路径。

| 构建 | FULL 握手时延（7 轮取最小） | 实测区间 |
|---|---|---|
| `notab`（关闭 comb） | **6.53 ms** | 6.53–9.38 ms |
| `opt`（启用 comb） | **4.00 ms** | 4.00–6.12 ms |
| 提升 | **1.63×** | — |

- RESUME/PSK 全程 0 次 SM2，故不受 comb 影响；两者把手握压到 1/0-RTT，线上字节降至 36%/40%。
- 时延为本机 UDP 环回实测，随主机负载有毫秒级波动，故取多轮最小值；握手字节与 SM2 计数为确定值。

## 7. 功耗估算（能量模型，**非实测**）

模型：`E(op) = cycles/op × E_cycle`，`E_cycle = V × I_dyn = 3.0 V × 100 µA/MHz = 0.30 nJ/cycle`，
`f = 26 MHz` 时平均功耗约 7.80 mW（Cortex-M4 典型参数）。将 V/I 替换为板级实测值即得实测结果。

### 7.1 协议侧（按 FULL 握手的真实运算构成折算）

> 口径修正：早期版本按"5×sign"估算 FULL 握手能耗，会系统性偏差。
> 现按 `dtlcp_hs.c` 的实际构成计算：**2×keygen ＋ sign ＋ verify ＋ ecdh ＋ 60 µJ 固定 KDF 开销**。

| 模式 | 握手能耗 (µJ) | 日通信总能耗 (µJ) | 占 2×AA 电池(2000mAh@3V=21600J) |
|---|---|---|---|
| FULL（2×keygen+sign+verify+ecdh） | **2290** | 8050 | 0.00004% |
| RESUME（0×SM2） | 60 | 5820 | 0.00003% |
| PSK（0×SM2，0-RTT） | 60 | 5820 | 0.00003% |

**同口径 REF → OPT：FULL 握手能耗 5646 µJ → 2290 µJ（2.47× 降低）。**

场景：低功耗传感终端 5 分钟 1 条遥测（日 288 条，单条约 20 µJ）。

- **comb 的副作用（如实披露）**：FULL 握手变便宜后，**会话恢复的相对收益缩小**——
  RESUME/PSK 日能耗从"约为 FULL 的 44%"变为"约为 FULL 的 72%"。这不是退化，
  而是"两条路都变快"的必然结果：绝对能耗仍然是 RESUME/PSK 最低（5820 µJ）。
- 绝对量级提示：三类模式日能耗均在 mJ 量级，占电池容量比例在 10⁻⁵ % 量级，
  说明**该场景下电池寿命由休眠电流而非密码运算决定**——不应把密码优化宣传为续航提升手段。

## 8. 结论与优化空间

**结论**：

1. **正确性**：6 个内核变体 + DTLCP 36 项全绿，KAT 与 OpenSSL 3.2.4 交叉一致，差分指纹逐位一致，
   负向输入全拒绝；comb 预计算表另有生成时自检与 CI 一致性断言。
2. **算力（本库内 REF→OPT）**：SM2 keygen **3.67×** / sign **3.31×** / verify **2.32×** / ECDH **1.44×**；
   其中 comb 表使 keygen/sign 再快 **2.63×/2.31×**。SM4 T-table **1.75–1.93×**。
   SM3 在 x86-64 上略慢（0.92–0.94×），**如实报告**，其价值在内存与 MCU 侧（待板上验证）。
3. **算力（对外部基线 GmSSL 3.1.1）**：SM4 打平或略胜（1.05–1.12×）、SM2 基点乘快 **1.61×**、
   验签持平（1.03×）；**SM3 慢 0.87×、变基点乘慢 0.62×**——根因已定位为**域运算慢 2.0–2.2×**
   （§4），这是下一轮第一优先优化项。
4. **内存**：全功能 26572 B Flash / 4128 B RAM，最小裁剪 20864 B / **0 B RAM**；
   comb 表用 3096 B Flash 换 RAM 零代价。最大调用路径栈深 3280 B（CT 构建 3440 B）→ 建议任务栈 ≥5/6 KB。
5. **协议**：comb 使 FULL 握手 6.53→4.00 ms（1.63×）；RESUME/PSK 把手握压至 1/0-RTT、0 次 SM2，
   线上字节 1198 → 428/474 B。
6. **功耗（估算）**：FULL 握手能耗 REF→OPT 降低 2.47×。

**优化空间（已核实，按投入产出排序）**：

- ✅ **已实现**：基点 comb 预计算表（本轮）。
- 🥇 **第一优先：域运算改造**（唯一由外部基线量化出来的瓶颈）。GmSSL 的 `fe_mul` 为 255 cycles，
  本库 561（**慢 2.2×**），且本库 OPT 的折叠约减甚至略慢于 REF 的试商长除法（561 vs 533）。
  改造方向：把"多轮折叠 + 试商收尾 + 两次条件减"改为**一次到位的 Solinas 归约**
  （GmSSL 的做法：`r[i] = s[i] + s[8..15]` 组合，无循环、无试商），或改用 Montgomery 域。
  预期把 `fe_mul` 拉向 254–300 cycles，从而同时改善变基点乘（0.62×→有望 >1×）、验签与基点乘——
  **收益覆盖全部 SM2 操作，比继续优化标量乘算法更值**（标量乘算法已优于 GmSSL）。
- ✅ **已用尽：批量求逆**。经代码核实**无适用目标**——单次 sign/keygen/verify/ECDH 各只有 1–2 处求逆，
  且 sign 的两处分别模 p 与模 n（不可合并）；唯一"多逆元同时出现"的场景（comb 表构造）
  已在生成器里用 Montgomery 批量求逆实现（31 次求逆 → 1 次）。
- ⏳ **更快的单次求逆**：`fe_inv` 本库 195,409 vs GmSSL 94,310（慢 2.1×）。除域运算改造外，
  改用二进制扩展欧几里得（约 170 轮，同时把 688 B 栈降到约 350 B）可再省约 10%。
  **代价**：该算法天然变时间，需为 `SMC_SM2_CT=1` 保留 Fermat 路径，形成双实现。
- ⏳ **MCU 板上实测**：`embedded/` 已预留 DWT 周期计数与 port 接口；**SM3 展开类优化与折叠约减
  在无硬件除法 MCU 上的收益待板上验证**——注意 §3.4 已表明折叠约减在有硬件除法的 host 上是负收益，
  因此该"MCU 上更优"的说法目前只是**待验证假设**，不应作为结论引用。
- ⏳ **与 TLCP 标准实现的互通**：DTLCP 为兼容子集，若复赛方提供参考实现可做互通测试。

## 附：侧信道执行路径相关性实验（`apps/bench/bench_sct.c`）

指标①为**确定性操作计数**（可复现，不受机器噪声影响）；指标②为交错采样的时间分布（参考）。
本轮实验**同时覆盖两条标量乘路径**——只测通用路径会漏掉签名的主路径（comb）。

### 指标①：操作计数（64 个 nonce，含随机与极端值）

| 标量乘路径 | 构建 | 点加 最小/最大/极差 | 倍点 最小/最大/极差 | 判定 |
|---|---|---|---|---|
| 通用 `sm2_scalarmult_jac`（tP 腿） | CT=0 | **5 / 58 / 53** | 250 / 258 / 8 | **随秘密变化** |
| 基点 `sm2_scalarmult_base`（k·G） | CT=0 | **2 / 51 / 49** | 51 / 51 / 0 | **随秘密变化** |
| 通用 `sm2_scalarmult_jac` | CT=1 | **78 / 78 / 0** | **257 / 257 / 0** | **恒定** |
| 基点 `sm2_scalarmult_base` | CT=1 | **78 / 78 / 0** | **257 / 257 / 0** | **恒定** |

| 极端 nonce | 通用 add / dbl | 基点 add / dbl |
|---|---|---|
| n−1 | 31 / 258 | 51 / 51 |
| 稀疏 0x8000…0001 | 5 / 257 | 2 / 51 |

### 指标②：时间分布（64 输入 × 12 轮交错采样，取每输入最小值）

| 标量乘路径 | 构建 | 均值 cycles | CV | 极差/均值 |
|---|---|---|---|---|
| 通用 | CT=0 | 1,984,067 | 0.0351 | 0.2520 |
| 基点 | CT=0 | 828,259 | 0.0551 | 0.4563 |
| 通用 | CT=1 | 2,120,271 | 0.0351 | 0.2973 |
| 基点 | CT=1 | 2,312,893 | 0.0318 | 0.2689 |

### 结论

1. **默认（非 CT）构建存在可观测的执行路径差异**——通用路径点加次数随 nonce 在 5–58 间变化，
   基点 comb 路径在 2–51 间变化。**本报告不声称默认构建抗侧信道**；这正是提供 CT 构建的理由。
2. **`SMC_SM2_CT=1` 把两条路径的执行路径都与秘密解耦**：运算次数恒定（78 add / 257 dbl）、
   表访问为全表 cmov 扫描（访存模式恒定）。
3. **常量时间的代价**：基点乘 828k → 2,313k cycles（**约 2.8×**），比 comb 前的代价（约 +35%）显著上升——
   因为性能路径变快了，而常量时间路径无法利用查表。这是"性能 / 抗侧信道"取舍的**定量依据**，
   在 `smc_config.h` 一键切换。
4. CI 对以下断言自动校验：CT=0 两条路径均"随秘密变化"、CT=1 两条路径均"恒定"。
